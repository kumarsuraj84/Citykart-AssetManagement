## What is NOT done / open

- Public access: the DNS A record and the router forward 3211 -> 10.0.1.98 are the user's steps (confirm they exist before sharing the link). The site is plain HTTP, so logins cross the internet unencrypted; HTTPS in front of it is a recommended later step. If the address changes, update `BASE_URL` in `shared\.env` and restart `CKAM-Web`, and note that any Asset Detail QR **and any label printed in the default "Barcode + QR" format** already printed or saved keeps the old address (keep the old address redirecting, or re-label) *(updated 2026-10-17, security release, GT-F02)*.
- HTTPS (decision deferred by the user, 2026-10-08). Notes for later: the certificate is installed on the app server only, never on users' devices, as long as it comes from a public CA (a self-signed or internal-CA certificate would need installing on every device). Options: an existing `*.citykartstores.com` wildcard, Let's Encrypt (port 3211 means the domain proof must be a DNS record, so automation needs DNS API access, otherwise a manual TXT record every 90 days), or a paid 1-year certificate. Serve it either from uvicorn (`--ssl-certfile/--ssl-keyfile`) or via Caddy in front. Then set `COOKIE_SECURE=true` and `BASE_URL=https://ckam.citykartstores.com:3211`. Port 3211 becomes HTTPS-only (`http://10.0.1.98:3211` stops working; by IP the browser shows a name mismatch), and renewal must be automatic or scheduled or the site goes down at expiry.

## Deploying a new version

Reference scripts (IF-15, 2026-10-16): `ops/windows/` holds secret-free reference versions of the launcher, the
release script, a read-only `verify_release.ps1` and a rollback script, matching the steps below; the runbook is
`docs/ai/CKAM_RELEASE_RUNBOOK.md` section 0. **CODE/REFERENCE SIDE FIXED — LIVE LAUNCHER STILL REQUIRES EXT-13**
(the server's own `shared\run_ckam_web.ps1` and task have not been compared with them; until then the live launcher
also still lacks `--no-proxy-headers`, N2 / EXT-38).

1. Develop and test on the dev PC only. Get the user's explicit OK before any `git push` and before any deploy.
2. Build `frontend` (`VITE_APP_VERSION=<sha> npm run build`, then `npm run check:build`), package `backend/{app,alembic.ini,pyproject.toml,constraints.txt,VERSION,scripts/create_owner.py}` and `frontend/dist` (as `frontend-dist`) into `releases\<sha>\`. *(updated 2026-10-17, security release: `backend/constraints.txt` (the exact tested package versions) and `backend/VERSION` (the release sha) must be in the package.)*
3. On 10.0.1.98: back up first (run `CK_Backup_CKASSETMANAGEMENT` on the DB server and confirm `backup.log` says OK), stop `CKAM-Web` (CKAM's own listener only), install the new backend into `shared\venv` **with the tested versions**: `pip install -c <release>\backend\constraints.txt -e <release>\backend`, set `FRONTEND_DIST_DIR` in `.env` to `<new release>\frontend-dist` (and `APP_VERSION=<sha>`), run **`alembic upgrade head` BEFORE starting** any new code (it needs the `.env` values in the process environment; check `alembic current` = `alembic heads` afterwards), then start `CKAM-Web`. The launcher must start uvicorn with **`--no-proxy-headers --no-server-header`**. **Keep the previous release folder AND the new release folder** (the editable install points the venv at the new `backend` folder; the previous one is the rollback path). *(updated 2026-10-17, security release)*
   **`FRONTEND_DIST_DIR` is the single switch for the release:** the launcher (`shared\run_ckam_web.ps1`) runs the backend from the `backend` folder next to it. (Until 2026-10-09 the launcher had the old release folder hard-coded, so the frontend updated but the API did not. Always verify below.)
4. Verify the NEW code is really running **on the migrated database**, not just that the site answers *(updated 2026-10-17, security release: `/openapi.json` can no longer be used, because from the security release on `/docs`, `/redoc` and `/openapi.json` are a JSON 404 in production)*: `/api/health` is ok; diagnostics health (`GET /api/admin/diagnostics/health`, signed in as a head-office admin) shows the new **version**, **environment `production`** and **migrations ok**; the served `index.html` references the new bundle name (bundle hash); the launcher log says `serving release: <new>` and its NAS login line succeeded; the QR direct link `/assets/<id>` opens the asset page. A green `/api/health` alone proves nothing: new code on an un-migrated database also answers it, but nobody can sign in (gate rehearsal GT-F05). Full list: `docs/security/CKAM_URGENT_PRODUCTION_SECURITY_RUNBOOK.md` step H.
5. Rollback: set `FRONTEND_DIST_DIR` and the editable install back to the previous release folder and restart the task. Database changes are never auto-reversed (restore from a verified backup only if truly needed). *(updated 2026-10-17, security release: for the security release a code-only rollback after its migrations is unsafe; the old release `3b5e842` can still receive but cannot move, sell or scrap on the new schema, and it reopens IF-01. Roll forward first: `docs/security/CKAM_PRODUCTION_ROLLBACK_STRATEGY.md`.)*

### Deploy notes added 2026-10-14 (release 3b5e842)

* The release script (stop task, backup `.env`, set the settings above, `alembic upgrade head` as the app role, start, verify, automatic rollback of the settings on failure) ran in about 30 seconds of downtime; checks used: `alembic current` = head, `/api/health`, `/openapi.json` lists the new routes, the served bundle is from the new release, `X-Request-ID` is on responses, launcher log says `serving release`, NAS mapping succeeded, `system_event` shows `app_started` (version, production) and the ERP copy `sync_success`. *(The `/openapi.json` check worked for `3b5e842`; it does not from the security release on, where it is a JSON 404 in production: use step 4 above. Updated 2026-10-17, security release.)*

* Production holds one company (`CKS`, ERP code `CKSPL`); the second company (CKVPL), cost centres, stock rooms, groups, Items and vendors still have to be set up by the head-office admin (the "Set up CKAM" wizard under Settings does this).
* Remaining manual items: PostgreSQL slow-query / lock logging on 10.0.0.205 (settings in `LOGGING_AND_DIAGNOSTICS.md`), an off-server copy of the nightly dumps, HTTPS.

## Rules

- Touch only CKAM's own folder, database, NAS folder, task and firewall rule on the shared servers.
- `alembic upgrade head` and `scripts/create_owner.py` print one-time passwords. Capture them to an admin-only file, never into reports or chat.
- Superuser database steps are run by the user on 10.0.0.205 (they type the `postgres` password).
