# CKAM — Production Server Readiness Checklist

Prepared during AM-10. This lists what the actual production server needs
before cutover — it does **not** claim the current dev/UAT machine already
satisfies every row; several rows are explicitly marked as needing
verification on the real target server, since this session runs inside a
development sandbox, not the eventual production host.

| Item | Requirement | Evidence from this session | Production action |
|---|---|---|---|
| OS/host | Any OS that runs Docker Engine + Docker Compose v2 (Linux, Windows, or macOS — the stack is fully containerized, no OS-specific code) | This dev sandbox runs Windows with Docker Desktop. `docker-compose.yml` has no OS-specific paths, volumes, or commands. | Confirm the target server has Docker installed and the operator who will run `docker compose` commands has been identified. |
| Docker version | Docker Engine supporting Compose v2 syntax (`docker compose`, not the legacy `docker-compose` binary) | This session: `Docker version 29.8.0, build 88096ef` — confirmed working with the full stack throughout AM-09 and AM-10. | Verify the actual production server's Docker version with `docker --version`. Any reasonably current Docker Engine (released within the last ~2 years) is expected to work; there is no version-specific feature this app relies on beyond standard Compose v2 syntax and healthchecks. |
| Compose version | Docker Compose v2 (bundled with modern Docker Desktop/Engine, invoked as `docker compose`, not `docker-compose`) | This session: `Docker Compose version v5.5.1`. | Verify with `docker compose version` on the production server. |
| Disk capacity | Enough free space for the `db_data` volume (grows with asset/event/holder count), the `uploads` volume (grows with document uploads), backup retention (14 days × 2 files/night), and Docker's own image layers | Current dev `db_data` volume: 95.3 MB (159 test assets, 305 test holders, 231 events). Current `uploads` volume: 18 bytes (0 real documents uploaded). These numbers are **not** representative of eventual production scale and must not be used for production capacity planning — see §21 of the AM-10 report for the explicit caveat. | Before go-live, estimate real expected asset/holder/document counts from CityKart's actual fleet size and confirm the target server has headroom well beyond that (a specific number is a business estimate, not something this audit can fabricate). |
| Backup disk/path | A path on a **different physical disk** than the one holding Docker's volumes, itself copied off the server | Current dev `BACKUP_DIR` is the compose default `./backups`, same disk as everything else — explicitly DEV-ONLY, see `CKAM_PRODUCTION_ENVIRONMENT_CHECKLIST.md`. | Provision a separate disk or network path on the production server before first deploy; set `BACKUP_DIR` to it. |
| LAN hostname/IP | The address other devices on the CityKart LAN will use to reach the app | Current dev value: `http://localhost:3211` (loopback only — a placeholder, not usable by any other device). | Determine and set the real LAN hostname or static IP before the first `docker compose up`, and before printing any QR label. |
| DNS | Optional — a hostname (e.g. `assets.citykart.local`) is friendlier than a raw IP but not required; the app has no DNS dependency of its own | Not configured in this dev environment (uses `localhost`). | CityKart's IT team decision — a static IP is sufficient if internal DNS isn't already in place. |
| `WEB_PORT` | The one LAN-facing port; must be open in the server's firewall | `3211` (default), open and reachable within this sandbox's own network. | Confirm the production server's firewall allows inbound `3211/tcp` (or the chosen alternate) from the CityKart LAN. |
| Firewall | `db`/`api` ports (`DB_PORT`/`API_PORT`) must remain bound to `127.0.0.1` only — never opened to the LAN | Confirmed in `docker-compose.yml`: both `db` and `api` use the `"127.0.0.1:${PORT}:PORT"` binding form. Verified live: `db` is reachable within this sandbox only via the loopback-mapped port, not from another simulated host. | Do not remove the `127.0.0.1:` prefix from either port mapping in production without a specific, deliberate, firewalled reason (see `docs/deployment.md`'s own guidance on this). |
| Clock/timezone | The `backup` container's cron entry (`0 2 * * *`) fires in the **container's own timezone**, not necessarily CityKart's local time | Not explicitly set in `docker-compose.yml` — the `postgres:17-alpine` base image defaults to UTC unless a `TZ` environment variable is set. Not investigated further this session, since AM-10's scope is preparation/evidence, not a config change without explicit authorization. | Decide whether "2 AM" should mean 2 AM UTC or 2 AM CityKart local time, and set a `TZ` environment variable on the `backup` service if local time is intended. Document the choice. Flagged as a **go-live configuration item**, not a blocker (a backup at the "wrong" hour is still a nightly backup). |
| Persistent volume location | `db_data` and `uploads` are named Docker volumes — their actual host-disk location is managed by the Docker daemon, not a path this repo controls directly | Confirmed present and populated via `docker system df -v` (95.3 MB / 18 B respectively). | On the production server, confirm the Docker daemon's own volume storage root has adequate space (see "Disk capacity" above) — this is a Docker-daemon-level setting, not a CKAM-level one. |
| `.env` | Must exist on the server, copied from `.env.example` and filled in for real (see `CKAM_PRODUCTION_ENVIRONMENT_CHECKLIST.md`) | This dev environment's own `.env` exists but carries dev-only values for `POSTGRES_PASSWORD`/`BASE_URL`/`BACKUP_DIR`. | Copy `.env.example` to `.env` on the server and set every row of `CKAM_PRODUCTION_ENVIRONMENT_CHECKLIST.md` to a real production value. `.env` must never be committed to git (already gitignored). |
| Admin credential owner | Who receives the one-time `scripts.create_owner` temporary password | Not yet determined for the real deployment — the owner identity (`Ankur Pahwa`, `CS6872`) is hardcoded in `backend/scripts/create_owner.py` by design (see that script's own docstring). | Confirm who runs `docker compose exec api python -m scripts.create_owner` on the production server and how the printed one-time password is relayed to Ankur Pahwa out-of-band (not email in plaintext, not Slack — a phone call or in-person handoff is safest). |
| Backup ownership | Who checks `docker compose exec backup cat /var/log/ckam-backup.log` periodically | Not yet assigned — see the Operations Ownership Matrix in `AM-10_GO_LIVE_PREPARATION_REPORT.md` §40. | Name an owner and a check frequency before go-live (AM09-09 remains open otherwise — no automated alert exists). |
| Restore ownership | Who is authorized to run `ops/restore.sh` against the production database in a real incident | Not yet assigned. | Name an owner — this operation is destructive (`docs/deployment.md`'s own warning) and should have a single accountable operator, not "whoever is around." |
| Rollback operator | Who executes the rollback procedure (`docs/ai/CKAM_RELEASE_RUNBOOK.md`) if go-live fails | Not yet assigned. | Name an owner before go-live day, ideally the same person doing the deployment. |

No service this checklist does not already use (no reverse proxy beyond
the existing nginx, no external cache, no message queue, no additional
database) is required — CKAM's actual stack is exactly the four services
in `docker-compose.yml`: `db`, `api`, `web`, `backup`.
