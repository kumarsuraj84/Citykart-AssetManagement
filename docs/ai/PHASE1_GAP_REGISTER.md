# CKAM — Phase-1 Gap Register

Compiled during AM-11 (Phase-1 Development Continuation + Business Gap
Review). Every row is evidence-based: a live browser walkthrough finding,
a legacy ThreadERP domain comparison, a code-level check, or a
carried-forward, previously-documented technical finding — never a
speculative "a typical asset system might have this."

Priority values: **MUST HAVE** (blocks real Phase-1 daily operation),
**SHOULD HAVE** (a real, evidenced friction point; workable without it),
**PHASE 2** (a real concept, not needed for Phase-1's actual operating
scale/model), **NOT REQUIRED** (evaluated and found unnecessary for
CKAM's actual, deliberately-narrower scope).

## Phase 2 / deferred — real concepts, not needed for Phase-1

| ID | Area | Gap | Evidence | Business Impact | Phase-1 Priority | Recommendation |
|---|---|---|---|---|---|---|
| G08 | Custody model | ThreadERP separates "Asset User" (day-to-day user) from "Custodian" (accountable owner) as two distinct fields; CKAM has one `current_holder_id` concept (across 4 holder types: EMPLOYEE/STORE/IT_STOCK/INSTALLED). | ThreadERP's Add New Asset form (`Custodian` required, `Asset User` separately selectable). | CKAM's simpler single-custody model has been sufficient through every stage's UAT so far, and no CityKart-specific evidence of a real need for the two-role split was found. | **PHASE 2** (only if evidenced) | Do not implement without a specific CityKart operational example where "who uses it" and "who is accountable for it" genuinely need to differ and be tracked separately. |
| G09 | Asset model | ThreadERP supports multi-level Location (`Asset Location`, `Location 1`, `Location 2`) and a Parent/Child asset relationship. CKAM has one flat Location field and no parent/child linkage. | ThreadERP's Add New Asset form. | No evidence CityKart's Phase-1 physical layout needs more than one location level, or that any asset needs to be tracked as a component of another. | **PHASE 2** (only if evidenced) | Do not implement speculatively. |
| G10 | Asset model | ThreadERP has an "Asset WIP" (work-in-progress / not-yet-commissioned) status before an asset becomes a normal tracked asset; CKAM's `procure_assets` puts every created asset straight into `IN_STOCK`. | ThreadERP's Dashboard ("WIP Assets: 1") and `Transaction → Asset WIP` menu. | No evidence CityKart's procurement process has a meaningful "ordered but not yet received/commissioned" gap that needs its own tracked state — Add Asset already requires a purchase date and an initial holder, implying the asset is already physically present. | **PHASE 2** (only if evidenced) | Do not implement without a concrete CityKart example of assets sitting in limbo between purchase and being trackable. |
| G11 | Lifecycle / accounting | ThreadERP has AMC, Insurance, Market Valuation, Depreciation, Retrospective Effect, and Transfer To/From General Reserve — a full accounting-grade fixed-asset module. | ThreadERP's Transaction/Depreciation/Reports menus (extensively explored this stage). | **NOT REQUIRED** — this is precisely the scope CKAM's own locked V1 decisions already, deliberately exclude (`docs/ai/DECISIONS.md`: "No AMC/insurance. No depreciation/accounting."). This stage's legacy review **confirms**, rather than challenges, that exclusion — ThreadERP is a finance/accounting system; CKAM is a physical custody-lifecycle tracker. | **NOT REQUIRED** | No action — re-confirms an already-correct, already-locked scope boundary. |
| G12 | Workflow | ThreadERP has an approval workflow for both new-asset submission (`Asset Workflow → Submission Of Asset / Pending Approval`) and custody movement (`Asset Movement → Pending For Approval`). | ThreadERP's Transaction menu. | **NOT REQUIRED** — CKAM's own locked V1 decision is explicitly "No approval workflow in V1." Re-confirmed, not newly discovered. | **NOT REQUIRED** | No action. |
| G13 | Operations | ThreadERP has a formal "Asset Verification" / "Verified Assets" physical-audit workflow. | ThreadERP's Transaction/Reports menus. | **NOT REQUIRED for Phase-1** — CKAM's own `PRODUCT_CONTEXT.md` already states "No physical verification (but QR/barcode stays forward-compatible)" as a locked decision; QR generation already exists and works, so the forward-compatibility promise is already honored. | **NOT REQUIRED** | No action. |
