# AM-17 — Issues Found and Fixed

All four defects found during AM-17's current-HEAD UAT were fixed within
this same stage, per the AM-17 fix policy (root cause understood, no new
business decision required, narrow scope). None is P0. None is left open.
Full evidence for each is in `docs/ai/AM-17_BUSINESS_WORKFLOW_FINDINGS.md`
(DEF-01/02/03) and `docs/ai/AM-17_E2E_AND_SMOKE_FINDINGS.md` (DEF-04).

| ID | Priority | Area | Defect | Evidence | Root Cause | Fix | Commit | Retest | Blocking |

| DEF-01 | P1 | Purchase Orders (correctness) | PO Delivery Done did not inherit the Vendor from the parent Purchase Order — every asset created via PO Delivery silently got `vendor_id=NULL` even when the PO itself had a vendor set. PO Number/Date were correctly carried through; only Vendor was missed. | Delivered a PO line whose PO had `vendor_id` set via direct API; confirmed the resulting `asset.vendor_id` was `NULL` in the database. | `deliver_pending_assets` (`backend/app/purchase_orders/service.py`) built its `procure_assets()` payload dict without a `vendor_id` key at all — `procure_assets` already accepted and used it (Add Asset already passed it), it was simply never wired up for this one call site. | Router now passes `po.vendor_id` through to `deliver_pending_assets`, which includes it in the `procure_assets` payload, same as PO Number/Date already were. | `0ec05a9` | New test `test_deliver_inherits_vendor_from_the_parent_purchase_order` (`backend/tests/purchase_orders/test_delivery.py`), passing. Full backend suite 341→346, all green. | Was blocking (normal-workflow data-correctness defect on a core path); resolved. |
| DEF-02 | P2 | Reports / Export | The Field-Change Audit export (`GET /api/reports/export/field-changes`) had no Reason column at all — Reason is the sole discriminator between a controlled correction row and an ordinary edit row (`AssetFieldChange.reason`). Data was never lost (still visible via `GET /api/assets/{id}/changes`), just missing from this one export. | Exported the audit after performing a correction via the API; the returned workbook's header row had no "Reason" column. | `field_changes_to_xlsx` (`backend/app/reports/export_service.py`) never read `change.reason`, even though the `(AssetFieldChange, asset_code, actor_name)` row tuple it receives already carries it — no extra query/join needed. | Added a "Reason" column to the header and each row. | `0ec05a9` | Updated test asserts `None` for an ordinary edit's rows; new test `test_field_change_export_includes_correction_reason` asserts the Reason text for a correction. Both passing. | Not blocking (data was never lost, just not exported); fixed anyway as narrow and evidenced. |
| DEF-03 | P2 | Masters (company isolation) | A non-ADMIN staff member (IT_TEAM/VIEWER) could read another company's Cost Centres — the generic company-owned-master list endpoint enforced company scope on writes only; omitting `company_id`, or passing a different company's id, still returned every company's rows. Only Cost Centre name/code, no financial data, on that master. | An IT_TEAM token scoped to Company A called `GET /api/masters/cost-centers` with no filter and, separately, with `company_id=<Company B>`; both returned Company B's rows. | `build_master_router`'s generic `list_items` (`backend/app/masters/router.py`) treated `company_id` as a purely opt-in, client-controlled filter for every caller, including non-ADMIN ones, instead of pinning a non-ADMIN's read to their own `scoped_company_ids()` the way every write endpoint already does. | Reads of a company-owned master are now pinned to the caller's own company for a non-ADMIN (ADMIN, which is cross-company-unrestricted by design, is unaffected); a non-ADMIN's `company_id` query param outside their own scope is silently narrowed, not honored. | `0ec05a9` | 3 new tests in `backend/tests/masters/test_am08_cost_center_scoping.py` (omitted filter, other-company filter, ADMIN-still-unrestricted), all passing. | Not blocking (low-sensitivity read, not a write/authz bypass); fixed anyway as narrow, evidenced, and low-risk. |
| DEF-04 | P2 | Masters (frontend UX) | All 7 masters screens (Companies/Locations/Departments/Cost Centres/Categories/Subcategories/Vendors) share `MasterCrudScreen.tsx`; its Add/Edit `useMutation` calls had no `onError` handling and no error display in either dialog — a failed save (e.g. a duplicate code, already a controlled 422 server-side) closed with zero visible feedback, leaving the user unsure whether it saved or why it didn't. | Submitted a duplicate master code through the live Add dialog during the failure-path smoke; the dialog showed no error text and gave no indication the save had failed. | `MasterCrudScreen.tsx`'s `createMutation`/`updateMutation` never read `.isError`/`.error` in their JSX — every other mutation-driven dialog in the app already shows `{mutation.isError && <p role="alert">...}` (`CustomFieldsScreen`, `AddAssetForm`, `CodeRuleScreen`, `PurchaseOrderDetail`, `AssetDetail`); this was the one screen that never adopted the pattern. | Applied the same established pattern to both the Add and Edit dialogs; the dialog now stays open showing the server's own message so the user can correct their input instead of silently losing it. | `8547bb0` | 2 new tests in `frontend/src/components/master-crud/MasterCrudScreen.test.tsx` (Add-dialog error, Edit-dialog error), both passing. Full frontend suite 176→178, all green. | Not blocking (contained usability defect, obvious workaround — retry with different input); fixed anyway as narrow, evidenced, and consistent with an existing app-wide pattern. |
